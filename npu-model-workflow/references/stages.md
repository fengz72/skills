# 阶段与完成条件

| 阶段 | 主要角色与动作 | 完成条件 |
|---|---|---|
| 需求与设计 | SE 调查、访谈与设计；测试审查覆盖；主控组织确认 | 唯一路线、输入输出、可信参考、边界、性能契约与有限预算明确，关键要求有测试方法 |
| 适配与正确性 | 开发接入 runner 或最小脚本；测试从固定快照独立执行 | 实际可构建/加载/运行，约定覆盖和精度通过；证据身份和命令完整 |
| 性能基线 | 测试按契约压测与采集；SE 分析并推荐目标 | 有效负载—成功吞吐—p99 曲线与环境记录，最好可行点或明确尚无可行点 |
| 优化循环 | SE 候选、主控归并、开发隔离实现、测试独立复验 | 每个 OPT 有固定记录和证据；包含最终配置压力正确性、必要稳定性，冻结配置后的独立性能结果及接纳原因 |
| 集成与交付 | 指定开发集成新快照；测试用最终包复验；主控汇总 | 唯一最终配置与产物可复现，所有 OPT 各一份记录和一行汇总，功能/精度/压力/稳定性/性能分别有真实状态 |

完成某阶段的资料交接不等于功能或性能已经通过；NOT_RUN、失败和缺证据保留。正确性失败不能进入正式性能收益判定，其他已授权的调查可继续。

## 优化循环的决定

- 采纳以指定父快照为前提；旧父版本上的 PASS 不自动迁移到新的集成快照。
- 接纳依据是精度/资源约束内的实际收益和明确副作用。延迟降低但吞吐尚未增加，可说明为后续增载创造空间，不伪造容量提升。
- 初始没有可行点时，正确性/资源检查通过的中间版本可以阶段接纳为探索基线，仍标记性能未通过。已有可行交付基线不被不可行候选替换。
- 可组合候选形成新的 OPT，列明组成编号、依赖/互斥，重新构建与验收。单项百分比不能相加。
- 达到停止条件或预算耗尽时结束搜索，保留所有失败、退化和未尝试项；交付预算内最好已验收版本，不声称全局最优。无可行点就明确性能失败。

## 记录与交付

主控在 progress 的“调优清单”表中预分配唯一 OPT，随后创建 `experiments/OPT-001.md` 等文档；并行子任务不独立分配全局编号。每个记录固定七节，使用 [调优模板](../assets/optimization-record.md)。不同实现/父版本/组合另建编号，同版本复测追加独立 run 身份、原始结果和决定历史。

交付报告的“完整调优记录”表，每个 OPT 恰好一行链接，写一句话内容、父基线与结果、候选与结果、带方向的吞吐/p99 变化、是否纳入最终包及原因。退化、无显著变化、构建失败、未完成、曾接纳后撤回全部保留。缺数据写未运行/未测得，不填 0%。

`audit_records.py` 只核对清单、文件、汇总的逐编号覆盖与目标链接。测试角色另核对数字计算、搜索/验收用途、实际命令/退出码、版本和原始结果；主控检查最终采纳项与交付配置一致。仅有审核脚本成功不能宣布交付通过。
