# 流身份、同步与并行性

## 不混用三层身份

| 身份 | 意义 | 不能据此推定 |
|---|---|---|
| 编译逻辑流 ID | 图节点/任务的调度标识 | 不是实际 RT 执行队列 |
| 模型流索引 | 当前加载模型的流资源索引 | 不能与其他模型同索引合并 |
| RT 流 ID | 运行时实际队列身份 | 创建次数不等于模型并行度，也不证明实际 overlap |

每条映射附带主机/设备、PID、图或模型身份、加载/执行窗口和来源行号。ID 会在不同模型或不同生命周期重用。同一数字不能跨层或跨会话自动等同，Python/应用 Stream 也不能直接当成最终 GE 内部流。

## 建立映射

1. 先按本次构建与运行产物划定窗口。Session 以图/模型/执行身份；ATC/ACL 先确认 OM 对应构建，再核对运行模型。时间接近或模型名相同只作辅助，不能跨进程把日志拼成唯一会话。
2. 查 known/unknown 图入口、最终逻辑流分配、模型加载资源和显式绑定记录。已见版本线索有 `AssignStreamsForDynamicShapeGraph`、`Logical stream index`、`Collect rt2 stream`、`SplitRtStreams`；先核对当前日志语义。函数名出现本身不证明建立了绑定。
3. 根据显式记录填写“逻辑流 → 模型索引 → RT 流”。某一步不存在时该边标为未知，保留可确认的部分，不填默认 0。不凭指针数值相似、全局第一条日志或推测的创建顺序补映射。
4. 区分根图、动态外层、静态子模型及辅助/HCCL 流。重复资源摘要去重并保留原位置；冲突记录不能静默覆盖。没有明确图关系时，只报告可确认的同族或局部作用域，不能创造父子关系。
5. 若需要算子归因，用本图节点的逻辑流分配与任务记录关联实际执行；没有节点名的行只能支持流级事实。

编译阶段逻辑流数、模型资源申请数、实际创建总数和本次活跃流数分别报告。辅助流可能只负责资源维护。某版本的静态图物理拆流与动态调度策略不同，必须有具体拆分/绑定证据，不能由一个刷新函数名推定已拆流。

## 用时间线检验执行

- 日志解释资源与绑定；设备/Host trace 检查真正的并行、事件 record/wait、拷贝和同步。多个流可以完全串行，单流数也不能概括整个 Host/设备流水。
- 先核对数据/控制依赖和开始/完成边界，再解释等待。排除 Host 未及时提交、错误同步位置、依赖正确但缺工作等原因；等待不全是可移除开销。
- 多流 kernel 耗时不能直接相加成墙钟延迟。保留 overlap、关键路径和区间并集的定义，端到端 p99 从实际请求计时获取。
- 异步输出读取、缓冲回收和下一请求写入必须位于相应完成边界之后；需要时结合[内存与缓冲](memory.md)验证跨流所有权与事件依赖。

改变流或并发配置前核实当前入口和版本支持，记录参数作用域。修改后用目标并发及混合 shape 验证请求/输出对应、数据精度、错误/取消清理与稳定性，再用无调试采集开销的独立运行验证 p99 约束内吞吐。

报告给出分层流表、显式映射、辅助/未知数量、冲突、实际 overlap 证据和候选动作。缺流日志不等于单流；只确认资源分配而没有 trace 时，明确尚未确认实际并行收益。
