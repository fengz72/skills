# 动态 shape 与调度

## 分别建立四项事实

| 事实 | 证据与边界 |
|---|---|
| 源模型声明 | 输入/输出 shape、符号维度、维度关系和数据依赖 shape。ONNX 符号维度不等同于 GE 内部的 unknown 标记。 |
| 编译输入与产物 | 实际指定 shape/范围/档位，编译后的描述、图及子图。一次固定输入不证明支持范围变成静态。 |
| 本次运行路径 | 加载/执行器及 known/unknown 子图的日志或 trace。存在 known 子图不证明整个模型没有动态控制。 |
| 执行模式 | 当前入口下 `graph_run_mode` 等配置的值及同版本语义。推理/训练用途和静态/动态 shape 是不同维度，mode 值不能替代动态判定。 |

先检查设计约束与实际设置是否一致。动态 batch 档位可能由多个固定 shape 分支组成，报告“支持的动态范围/档位”和“本次激活的分支”，不要仅贴一个静态/动态标签。

## 定位步骤

1. 按本次编译/运行身份截取完整日志窗口，保留并行线程、子图、模型和时间信息；ATC 与 ACL 用 OM 身份关联，Session 用实际图与执行身份关联。
2. 在已有日志内检索 unknown 判定、强制标记、InferShape 和调度入口。可用 `rg -n -C 4 'SetGraphUnknownFlag|cannot support no tiling|force unknown|marked force unknown node forcibly|before_infer|after_infer' <本次日志>`；将占位符换成已确认文件。关键字来自已见版本，只是候选线索。
3. 检查来源层：形状推导产生 unknown；算子/引擎能力及 tiling 依赖；地址刷新能力；FE 强制设置；数据流或图级条件。总标记不足以区分原因，继续找同节点、同次构建的具体判定记录。
4. 沿图边和推导前后状态追溯产生未知形状或强制调度的节点。若来自子图则进入子图追溯。并行日志的全局第一条不是必然根因，下游级联标记不是各自独立根因。
5. 区分“输入本身动态”“推导精度不足”“数据依赖输出”“能力限制导致动态路径”。当前材料不能区分时保留候选和最小补采项，不为给出单一答案猜测。

日志级别不足、缺相关阶段或版本改名时，先检查当前运行环境的日志配置说明，按最小复现补采。不能用无关键字或空报告证明静态执行，也不必等待源码才能完成已被日志支持的阶段判断。

## 方案与复验

- 固定 shape、分档、常量整理或替换节点均是待验证候选。先检查允许修改范围及全部输入约束，禁止暗中缩小支持范围。
- 一个算子在静态输入时仍可能被强制动态调度；解释它的当前能力约束，不能机械地推荐“把输入改固定”作为必然修复。
- 修改后保留编译图/执行路径变化的证据，覆盖边界、混合 shape、分档切换与动态输出，检查业务精度和缓冲容量。
- 性能计时按既定契约处理首次执行和缓存。正常测量窗口内真实出现的新 shape 编译、缓存未命中与加载耗时不可事后删除；冷启动另按需求验收。

输出至少列出四项事实、触发链、具体节点或未定位原因、日志行、版本核实来源、方案适用条件与验证结果。
