# 单设备任务：互斥、身份和取消

已有可靠的资源平台时优先使用它。没有时，可用包内 `scripts/device_job.py` 包装一次有限时长的构建、验证或测量命令。它是 Python 标准库的 POSIX 小工具，不提供调度服务，也不判定模型或 NPU 验收通过。

## 在实际执行环境启动

必须在真实执行主机和选定容器内运行，显式给出 cwd；不能只在 Agent 本机给 SSH 命令加锁。所有会使用同一物理设备的任务需要采用同一锁协议、共享同一个支持 `flock` 的目录，并使用一致的物理设备身份。容器内的逻辑编号 `0` 不一定对应同一张物理卡；优先由环境调查确认芯片/设备 UUID 或宿主机与物理卡的稳定标识。

```sh
python3 <本skill根>/scripts/device_job.py run \
  --cwd /absolute/model-project \
  --run-dir /absolute/model-project/work/OPT-001/run-001 \
  --lock-root /shared/npu-workflow-locks \
  --device host-A/physical-device-UUID \
  --timeout 600 --grace 3 \
  -- python3 benchmark.py --config configs/final.yaml
```

`run-dir` 必须是新目录。`--timeout` 是从监督进程启动算起的锁等待加实际任务时限，必须为有限正数；`--grace` 是 TERM 后升级为 KILL 的等待时间。同一任务用多张卡时重复 `--device`，脚本按统一顺序获取全部锁以避免交叉死锁。命令按 argv 传入，不使用 `shell=True`。需要管道或重定向时，优先在任务自身脚本中实现，不拼接来源不明的 shell 文本。

不要把口令或 token 放在命令参数中：脚本会保存 argv 以便复现。它不会导出全环境，任务本身的日志仍由调用者检查并按项目要求保护。运行依赖为 Python 3.8+、POSIX 进程组、`fcntl.flock`，非 Linux POSIX 主机另需系统 `ps`；不支持 Windows。

## 真实执行与锁的生命周期

前台调用端启动一个脱离控制终端的监督进程。监督进程获取锁后，在独立进程组启动任务；在任务执行、超时、取消和清理期间持续持锁。它保留未回收的直接子进程身份，直到所有组信号结束，避免 PID/进程组号复用后误杀其他任务。

- 正常结束：确认任务进程组无活跃成员，再回收直接子进程、关闭锁 FD 和写入最终状态。
- 超时、SIGTERM、SIGINT 或 SIGHUP：调用端转发给监督进程；监督进程只停止本任务进程组，先 TERM，再按 grace 升级 KILL，确认组内活跃工作结束后释放锁。
- 调用端被硬杀、SSH 断连而调用端没有机会处理信号：监督进程继续持锁并执行有限时限，或接受 run 目录中的取消请求。SSH 返回不是远端任务完成证据。
- 直接命令退出却留下同组后台进程：监督进程清理它们，返回 `125`，避免把不完整的任务生命周期报告为成功。
- 进程无法终止，或无法确认组成员：保留锁并报告 `cleanup_blocked` / `verification_blocked`；观察器异常不阻止自有进程组在 grace 后升级 KILL，但只有恢复确认后才释放锁。任务时限不是不经核查就抢占设备的租约。

锁 FD 也传给直接任务，作为监督进程意外硬退出时的额外保护：只要直接任务仍持有该 FD，锁不会仅随监督进程退出而释放。监督进程自身遭 SIGKILL 时不能执行清理，状态会停在最后一次记录，前台返回未确认错误；**此时必须核查实际任务和设备，不能把旧状态当完成证据。** 直接任务主动关闭继承 FD、逃逸进程组的 `setsid`/双重 fork daemon、跨 PID namespace 的逃逸和强制杀死所有持锁进程均不在保证范围内。被包装的 runner 应保持工作前台运行，不脱离进程组；有此类需求时改用现成作业平台/cgroup 等真实任务句柄。

文件存在和 owner 内容都不是锁仍被持有的证明，旧锁文件也不是死锁。不要删除或按时间抢占锁文件，否则不同任务可能锁住不同 inode。默认锁文件权限为 `0600`，面向同一执行用户/UID 的合作任务；跨 UID 的设备调度应使用既有资源平台或由管理员先配置并验证相应共享权限，不能假定默认配置支持。跨容器未共享锁目录、不同设备别名、不同锁根路径、不遵循协议的外部任务、网络文件系统锁语义异常，都会破坏互斥；上线前在实际环境验证争用。

## 取消、证据和恢复

```sh
python3 <本skill根>/scripts/device_job.py cancel \
  --run-dir /absolute/model-project/work/OPT-001/run-001
```

取消通过受保护 run 目录中的任务 ID 请求文件完成，不从旧 JSON 读取 PID 再发信号。`cancel` 的退出码 0 只表示请求已写入；随后读取 `status.json`，等待真实监督进程报告 `finished`。没有活着的监督进程时，请求本身不能清理工作，应依据真实主机/容器任务句柄核查。

每个 run 目录包含：

| 文件 | 含义 |
|---|---|
| `request.json` | task ID、argv、cwd、物理设备身份、锁根目录与时限 |
| `status.json` | 实际主机、监督/任务进程身份、PGID、阶段、原因、退出码、时间和结束核对结果 |
| `task.log` | 任务 stdout 与 stderr |
| `supervisor.log` | 包装器异常日志 |
| `cancel.json` | 存在时表示已提交取消请求，不代表已结束 |

Linux 身份同时记录启动 ticks 与 boot ID；其他 POSIX 平台记录 PID 与观察时间。实际取消不依赖磁盘中的 PID。run 目录应由任务用户管理，不允许其他任务覆盖。`finished` 表示受管进程组已经停止；`device_release_checked` 固定为 `false`，因为脚本没有 NPU API，也不能确认驱动中异步工作、设备错误或其他作业。

包装器入口恢复 `SIGCHLD` 默认处理，避免继承 `SIG_IGN` 在 Linux 自动回收子进程、丢失失败退出码并破坏未回收组长身份的前提。

正式排下一次设备任务前，测试/主控仍需在实际环境检查任务日志结尾、退出码和真实设备工作/资源状态，记录核对结果。发现残留工作或设备状态不明时保持资源为“待核查”，暂停派发；该脚本的 OS 锁不等于 CANN 设备释放证明。需要驱动级完成确认和跨不合作任务独占时，使用实际资源平台的释放机制。

退出码：原任务正常退出时保留其退出码；任务信号退出映射为 `128 + signal`；超时 `124`；遗留同组后台进程 `125`；文件取消 `130`；内部异常或监督状态未确认 `70`。原任务若恰好返回这些数字，应结合 `reason` 和 `task_returncode` 区分。

## 随包 CPU 回归

```sh
python3 -m unittest discover -s <本skill根>/tests -p 'test_device_job.py' -v
```

覆盖同物理设备互斥、成功与失败证据、锁等待超时、TERM/HUP、忽略 TERM 的任务与孙进程、调用端硬退出后的监督与锁保持、监督进程硬退出后的直接任务继承锁、取消不信任磁盘 PID，以及命令留下后台子进程的清理。这些测试仅使用 CPU 进程与临时锁，不占用 NPU。随本次实现已在 macOS/Python 3.13 与 Linux 容器/Python 3.11 执行，仍不能代替真实设备完成与释放验证。
