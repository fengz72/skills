# p99 约束下的吞吐测量

目标是固定工作负载、精度与资源，最大化满足 p99 上限、错误/超时和稳态约束的成功业务吞吐；不是峰值提交 QPS 或最小平均耗时。SLO、统计量、预算与输入分布由单模型设计确定。

用户明确暂不设置 p99 上限时，设计中记录“未设置”，按约定范围探索成功吞吐并持续报告 p99；不擅自填写上限，也不声称已通过延迟 SLA。依赖数值上限的统计辅助不能原样充当该场景的 SLA 判定。

## 测量前固定

先通过 [设备可用性门禁](orchestration.md#设备可用性门禁)。所有授权候选 NPU 被其他进程占用时，性能测试保持未运行，先完成设计和离线准备；获得可独占设备并重新核查后再开始。

- 计时起止与单位；模型执行与服务端到端分别定义。应计入的排队、批处理等待和前后处理不能藏到起点之前；异步调用必须计到约定的输出就绪/响应完成，不以提交返回为终点。
- 代表性输入 shape/长度/值分布、到达模型/突发、业务吞吐单位，以及实例/batch/并发/调度搜索范围、物理设备/核/内存预算。
- 起始缓存、预热覆盖、冷启动场景。只排除约定启动段；测量窗口内真实发生的新 shape 编译、缓存未命中和加载保留。
- 窗口、请求数、重复轮次、p99 算法/跨轮与分组规则、误差和积压判据。不要平均多轮 p99 冒充合并分布，也不从五条样例或几次调用推断正式尾延迟。

开放到达应记录计划到达、实际发送、接收和完成，核对负载发生器能力、发送滞后和漏发。发生器没有实际施压的点无效；闭环并发和开放到达分别标记。不同机器时钟须有可信对齐，不减去不同未对齐时钟的时间戳。

窗口结束仍未完成的请求继续跟踪至响应/超时，不能只计算较快完成子集；同时记录队列、在途与等待，判断是否持续增长。有限批次排空后的请求数除以发送窗口不是可持续容量证明。错误/超时不能静默剔除以改善 p99。

## 搜索、验证与接纳

先粗到细搜索并记录全部运行点，再冻结候选/参数，用同一契约分布下独立请求序列/随机种子和新轮次验收。基线同规则，必要时交错复测消除漂移。正式收益引用验收值，不选搜索中最好一轮代替。只有一份确定性数据时至少独立重测，并说明缺少独立数据的结论范围。

同负载 A/B 固定到达率与相关参数用于解释变化；容量比较按同样规则分别寻找并复验最佳可行点。不同容量点的 p99 差异不解释成同负载延迟收益。初始无可行点先改可行性，首次可行写状态转变，相对容量提升不适用。

数字位于约定波动范围时记录观测差值和“无显著变化”。最终配置做 [压力正确性与稳定性](correctness.md)，组合另验；profiling 用于解释，与正式 benchmark 分开。实际设备外部负载、Host 压力和构建负载可污染测量，记录并排除无效轮次。

## 可选请求统计辅助

`scripts/request_metrics.py` 是纯 Python 标准库辅助，不提供负载发生器，也不自动判定整体模型验收。它读取一轮最终归档的 JSONL，每个业务请求恰好一行，最小字段：

```json
{"request_id":"req-1","phase":"measure","status":"success","scheduled_ns":1000000000,"sent_ns":1000000100,"received_ns":1000000200,"completed_ns":1005000000}
```

`phase` 显式为 `warmup` 或 `measure`；预热必须由测试前的规则决定，不能事后把慢请求改标预热。`status` 为 success/error/timeout/pending，超时也记录实际结束时刻。所有时间戳使用同一已对齐时钟的整数 ns；`received_ns` 在从接收开始计时时必需。仍 pending 的 cohort 不给部分 p99。

```text
python3 <本skill根>/scripts/request_metrics.py --requests <请求JSONL> \
  --window-start-ns <整数> --window-end-ns <整数> \
  --expected-requests <计划请求数> --min-requests <契约最小数> \
  --p99-limit-ms <上限> --max-send-lag-ms <发生器滞后上限> \
  --latency-start scheduled_ns --max-error-rate <契约比例> --out <新结果文件>
```

用实际计划请求数检查漏发；已测行必须在该发送窗口内，其他段单独文件或明确 warmup。最近秩 p99 包含所有已归档请求的响应/错误/超时延迟。输出为数值约束结果、失效原因、窗口内成功完成速率、整个发送 cohort 的成功数/窗口时长和窗口结束在途数。**后者不能冒充稳态吞吐**，需要原始队列/负载与独立验收证据。统计脚本不是 profiler，不能从 kernel 日志伪造这些时间戳。

退出码 0 只表示本次输入的数值约束满足，1 表示无效数据或数值不满足，2 表示输入/调用错误。既有输出文件不覆盖。即使数值通过，测试仍核验真实完成边界、负载代表性、队列稳态、错误契约、压力正确性、稳定性与跨轮判据。
